## 实测发现与处理

### 1. 套餐字段不能单独用来判断是否收费

Railway API 返回 `plan=HOBBY`，同时返回 `isTrialing=true`、剩余 30 天与 5 美元额度、无付费订阅及默认支付方式。官方 Plans 页面显示 Trial，且已通过账号验证。因此将此次归类为免费试用，不能误判成已订阅 Hobby，也不能误判成正式 Free。

官方说明 Trial 在 30 天或额度耗尽后转入 Free；本次没有等待或模拟这一转换。[Railway Trial 规则](https://docs.railway.com/pricing/free-trial)

### 2. 配置文件有效，不等于平台已经采用

最初上传的 `railway.json` 符合公开 JSON schema，但实际部署未采用其中的休眠、健康检查和资源限制。查阅当日官方文档确认，新服务已不能采用旧 Config as Code；旧服务的兼容支持将于 2026-12-01 截止。[官方说明](https://docs.railway.com/guides/config-as-code)

已移除该文件，改用官方 `serviceInstanceUpdate` 和 `serviceInstanceLimitsUpdate`，随后重新部署并核对最终元数据。参数保存在 [railway-settings.json](cloud-tools/railway-settings.json)；这个文件是验证记录中的 API 参数，不是供应商自动读取的配置。

### 3. 本机传输失败与应用故障要分开判断

Railway 部分 CLI 请求、Python urllib 及一次 curl 请求出现连接或 TLS 握手超时。没有修改全局代理或关闭证书验证。基础设施变更结果不确定时先读取状态，没有盲目重复创建项目。

新增 [curl 传输适配](cloud-tools/curl-probe.py)，复用原有 HTTP 检查。仅对样例幂等请求的传输失败做最多两次重试，HTTP 错误直接保留。v1 的完整检查发生一次传输重试，最终 v2 检查没有重试。当前证据不能定位超时发生在本机代理、网络链路还是供应商侧。

Go 标准 logger 的正常 `listening` 事件写入 stderr，被 Railway 标成 error；该时刻健康检查和数据库读写正常。后续故障诊断应结合事件内容与实际健康状态，不能仅凭日志颜色判断故障。

## 只读网络诊断结果

用户授权比较当前代理与直连路径，并要求不修改系统代理设置。实测发现命令环境配置了本机 HTTP 代理，目标公网 IP 的路由仍经过 TUN；因此 `--noproxy` 仅绕过显式 HTTP 代理，固定公网 IP 也未构成独立的非 TUN 直连对照。

共执行 34 次 GET 请求，均未自动重试或关闭 TLS 校验。先做 4 次代理健康检查，再交替执行三种路径各 6 次健康检查，最后分别对两条绕过显式代理的路径各做 6 次数据库就绪检查：

| 路径 | 健康检查 | 数据库就绪 |
| --- | --- | --- |
| 显式 HTTP 代理 | 9/10 成功，1 次 TLS 超时（含最初 4 次基线） | 本轮未重复此组 |
| 不使用显式代理，沿用本机解析 | 6/6 成功 | 5/6 成功，1 次 TLS 超时 |
| 不使用显式代理，临时固定公网 IP | 6/6 成功 | 6/6 成功 |

失败均发生在 TLS 握手完成前，没有 HTTP 响应；成功请求均通过证书校验并返回 Go v2 或数据库 `ready`。这证明域名、证书和数据库连接可以正常工作，但当前访问链路存在间歇性失败，不能归因为数据库故障，也不能仅凭较短的固定 IP 样本锁定根因。三组均经过 TUN，尚不能区分本机域名分流、隧道出口、上游或远端边缘节点的影响。

没有修改系统代理、路由、DNS 或应用配置。固定 IP 仅用于诊断，不会写成产品默认连接方式。已在故障注入前继续暂停，等待用户切换代理节点后复测，或进一步授权只读检查分流规则。[汇总证据](results/network-diagnostics-report.json)
